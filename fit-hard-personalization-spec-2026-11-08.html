01. Product vision and architecture

The central concept

Fit Hard must operate as one connected system, not a collection of independent features.

The user's profile is the source of truth. The meal engine, workout engine, calendar, progression system, mascot and notifications all read from the same profile and update from the same underlying records.

PERSONAL PROFILE

Goals, body data, preferences, equipment, availability.

MEAL ENGINE

Calories, protein, recipes, ingredients and shopping.

TRAINING ENGINE

Muscle groups, splits, exercises and recovery.

PROGRESSION

Performance, weights, repetitions and adjustments.

CALENDAR

Meals, training, rest, appointments and tracking.

MASCOT

Recommendations, feedback and motivation.

Critical architecture rule

Never calculate different calorie targets independently in different screens. Never create a workout that ignores the user's equipment. Never generate a shopping list independently of the selected recipes.

All features must use shared services.

NutritionServiceCalculates energy, macros and meal targets.
RecipeServiceFinds, filters, scales and swaps recipes.

Implementation requirement: The app must work without an internet connection for core functions. Store the recipe database, exercise database, routines, profile, progress and calendar locally. Use optional synchronization if the existing app supports it.

Profile update behavior

  • Changing a goal triggers a recalculation of relevant targets.
  • Changing weight triggers updated nutrition estimates when appropriate.
  • Changing equipment triggers workout exercise substitution.
  • Changing training availability triggers schedule regeneration suggestions.

  • Changing allergies immediately removes unsafe recipes and substitutions.
  • Changing a meal does not unnecessarily change other meals.

Existing completed workouts and historical meal records must never be silently rewritten when a profile changes.

How the meal engine works

2. Calculate daily nutrition targets.
3. Read selected meal types.
4. Filter the recipe database.
5. Match ingredients and preferences.
6. Calculate recipe nutrition.
7. Generate shopping list.

Nutrition calculation

Estimate resting energy expenditure using a validated method, such as Mifflin-St Jeor, when its assumptions are appropriate. Estimate daily energy expenditure using activity information. Use observed weight trends to calibrate estimates over time.

The calorie target must depend on the user's goal, age, activity, weight, training and safety flags.

Do not impose aggressive deficits or guarantee a specific rate of weight loss.

For eligible exercising adults, a configurable protein starting reference can use 1.4–2.0 g/kg/day, adjusted for context and professional advice.

Calculate fats and carbohydrates from the remaining energy budget using a validated configurable nutrition policy. Never create macronutrient totals that exceed or contradict the calorie target without explaining rounding differences.

Exercise selection

The exercise database must contain enough alternatives to create varied routines while respecting equipment and experience.

Every exercise needs:

  • Exercise name.
  • Primary muscle group.
  • Secondary muscle groups.
  • Equipment.
  • Movement pattern.
  • Difficulty.
  • Instructions.
  • Technique cues.
  • Common mistakes.
  • Sets and repetition recommendations.
  • Rest recommendations.
  • Demonstration image or video, if licensed and available.
  • Alternative exercises.

Training volume rules

The engine should count both direct and indirect muscle work. For example, pressing exercises also involve triceps and shoulders. Do not count every compound set as a full direct set for every involved muscle.

For healthy adults seeking hypertrophy, approximately 10 weekly sets per muscle group is a useful evidence-based reference, not a compulsory starting target. Beginners may need less. Advanced users may tolerate different volumes.

Start conservatively and increase volume only when the user is recovering and progressing.

Routine duration

Create an initial four-week training block. Repeat effective exercises across sessions to make performance measurable. The user can continue a successful program beyond four weeks.

At the end of the block, evaluate:

  • Strength changes.
  • Completed sets and repetitions.
  • Recovery.
  • Training consistency.
  • Difficulty ratings.
  • Goal changes.

Generate a new block or maintain the existing program based on actual performance. Never automatically replace all exercises just because a calendar period has ended.

Routine generation result

Once generated, save every session to the Routines library and schedule it on the calendar.

06. Progressive overload engine

This is a core Fit Hard differentiator. The app should remember every exercise and help users make measurable progress instead of giving them the same static routine indefinitely.

Information to track per exercise

  • Weight used.
  • Completed repetitions.
  • Prescribed sets.
  • Completed sets.
  • Rest time.
  • Difficulty rating or RIR.
  • Exercise technique feedback.
  • Historical performance.

Double progression

Use repetition ranges and resistance increases as the primary progression method for appropriate exercises.

Example:

SessionWeightRepetitions
130 kg8, 8, 8
230 kg9, 8, 8
330 kg10, 10, 9
430 kg12, 12, 12
532.5 kg8, 8, 8

These are illustrative targets. A progression recommendation must also account for technique and perceived effort.

Progression rules

  1. Establish an appropriate starting weight or bodyweight variation.
  2. Set an exercise-specific repetition range.
  3. Track every completed set.
  4. When the user reaches the upper end of the range across all prescribed sets with good technique, assess whether a small resistance increase is appropriate.
  5. Recommend an achievable increase based on available equipment.
  6. After increasing weight, reduce the repetition target within the range if necessary.
  7. Record the new performance baseline.

When not to increase difficulty

  • Technique is deteriorating.
  • The user reports excessive fatigue.
  • Performance has repeatedly declined.
  • The user reports pain or injury.
  • The user has not completed the prescribed work.

Do not interpret pain as a normal training challenge. Stop the affected exercise and recommend appropriate professional advice.

Deload and recovery logic

A deload should be suggested when accumulated fatigue, performance decline and recovery feedback indicate that a reduction may help. It should not be forced automatically every fourth week.

Possible adjustments include reducing sets, reducing load, increasing rest or temporarily replacing a demanding exercise.

Progress display

Show:

  • Personal records.
  • Weight progression graphs.
  • Repetition progression graphs.
  • Training consistency.
  • Weekly completed volume.
  • Muscle group training history.

10. Medication and peptide tracking

Important medical and regulatory boundary: Fit Hard must not prescribe peptides, recommend experimental compounds, calculate injectable doses or supply default dosing protocols. In Australia, many peptides promoted for fitness, recovery and weight loss are unapproved therapeutic goods. The TGA warns about significant risks, including incorrect ingredients, unreliable labelling and serious adverse effects.

This feature should function as a private medication and prescribed-treatment tracking tool.

Medication section

Allow users to:

  • Add a prescribed medication or peptide by name.
  • Enter the product exactly as prescribed.
  • Record prescribed dosage and units.
  • Record route of administration as directed.
  • Record prescribed frequency.
  • Enter clinician-provided instructions.
  • Set reminder dates and times.
  • Record the prescribing professional if desired.
  • Pause or discontinue tracking.

Dosage entry

Support clinician-prescribed custom entries and unit selection. Do not offer generic recommended doses or prefilled injectable dosage protocols.

If the user changes their dosage, clearly explain that they must follow their prescriber's instructions.

Medication reminder interface

MY MEDICATION SCHEDULE

Medication name: User-entered prescription

Prescribed amount: User-entered amount and unit

Time: User-selected time

Frequency: User-entered prescribed schedule

Safety requirements

  • Never suggest changing a dose.
  • Never calculate injection preparation or reconstitution.
  • Never infer a dose from body weight.
  • Never recommend combining peptides.
  • Do not promote unapproved products as safe or effective.
  • Allow the user to record prescribed medicines without providing medical advice.
  • Provide links to official medicine information where possible.

Only populate an approved medicine catalogue using verified, current regulatory data. Do not represent an unapproved experimental peptide list as an approved treatment catalogue.

11. Mascot recommendation engine

Purpose

The mascot is the personality of Fit Hard and the user's personal fitness companion.

It must respond to real user activity and offer helpful, contextual recommendations.

Recommendation categories

SituationRecommendation
New userExplain their personalized training plan.
Workout completedCelebrate actual completed activity.
Personal recordHighlight the exercise and improvement.
Missed workoutOffer a practical rescheduling option without guilt.
Repeated fatigueSuggest recovery or reviewing training difficulty.
Low protein intakeSuggest a suitable recipe or food option.
Missing ingredientsPoint to the shopping list.
New training weekPreview the user's upcoming routine.
Completed milestoneCelebrate the milestone.

Recommendation rules

The mascot should only make statements supported by stored app data. It must never invent workout completion, weight changes or meals.

Examples:

  • "Your hip thrust improved from your previous session."
  • "You've got three training sessions planned this week."
  • "Your lunch is ready in your meal plan."
  • "You have two ingredients left to buy."
  • "You have completed all your planned workouts this week."

Motivational behavior

  • Celebrate consistency, not just weight loss.
  • Reward effort and measurable progress.
  • Use supportive, non-judgmental language.
  • Never shame users for missed days.
  • Never encourage dangerous restriction or overtraining.
  • Allow the user to reduce mascot interactions.

Implementation

Use a deterministic rule engine with prioritized recommendation templates. It does not require an AI API.

Store recommendation history to prevent the mascot from repeating the same message excessively.

12. Notification engine

Notification categories

  • Workout reminders.
  • Meal reminders.
  • Shopping reminders.
  • Recovery reminders.
  • Medication reminders.
  • Progress milestones.
  • Calendar activities.

Workout notifications

Allow users to select the reminder time before a scheduled workout. If the workout is rescheduled, update the notification.

Meal notifications

Remind users of meals at their chosen times. Do not force a fixed meal schedule. Use their actual calendar and meal preferences.

Medication notifications

Use the user's entered prescribed schedule. Never create medication reminders based on a generic peptide protocol.

Notification controls

  • Enable or disable individual categories.
  • Set preferred quiet hours.
  • Set notification frequency.
  • Change reminder times.
  • Dismiss or complete reminders.

Technical behavior

Use Apple's UserNotifications framework.

  • Request permission at the appropriate moment.
  • Explain why notification permission is useful.
  • Schedule local notifications.
  • Store notification identifiers against their source records.
  • Cancel outdated notifications.
  • Reschedule after calendar edits.
  • Handle timezone and daylight-saving changes.
  • Do not send duplicates.
  • Support notification action buttons where appropriate.

The app must continue functioning when notification permission is denied. Display in-app reminders instead.

Data integrity

  • Use stable identifiers.
  • Use database relationships rather than duplicate independent records.
  • Preserve completed workout history.
  • Use versioned profile and training-plan changes.
  • Prevent duplicate calendar events.
  • Recalculate derived nutrition values when ingredient quantities change.
  • Preserve medication records securely.
  • Provide backup and export options where appropriate.

Privacy

Fitness, weight, dietary and medication information is sensitive. Store only what is needed, use appropriate encryption and access controls, and obtain consent before using HealthKit or sharing data with external services.

15. UI and UX requirements

Overall design direction

Retain the existing Fit Hard brand, visual identity, mascot and working components wherever possible. Extend the current design rather than rebuilding it without a reason.

The experience should feel:

  • Modern.
  • Premium.
  • Motivating.
  • Friendly.
  • Clean.
  • Intuitive.
  • Visually rewarding.

Navigation

The user must be able to access the major areas without confusion:

  • Home.
  • Meals.
  • Routines.
  • Calendar.
  • Progress.
  • Medication tracking, if enabled.
  • Profile and settings.

Use the existing navigation architecture if it is already working. Avoid creating unnecessary duplicate destinations.

Design principles

  • One primary action per major screen.
  • Progressive disclosure of advanced settings.
  • Readable nutrition and training data.
  • Consistent category colors.
  • Accessible typography and touch targets.
  • Useful empty states.
  • Clear loading and error states.
  • Confirmation before destructive actions.
  • Persistent progress where appropriate.

Important empty states

Do not leave users with blank pages. If there are no meals, routines or calendar events, provide a clear next action.

16. End-to-end testing requirements

Mandatory: Every feature must be tested through actual user interactions, not just by checking whether the screen renders.

A. Onboarding tests

  • Complete onboarding with every supported goal.
  • Test different training frequencies.
  • Test all dietary patterns.
  • Test missing optional answers.
  • Test invalid and boundary values.
  • Confirm answers persist after restarting.
  • Confirm every answer reaches its correct service.

B. Nutrition tests

  • Generate meals for different goals.
  • Check calorie calculations.
  • Check protein, carbohydrate and fat calculations.
  • Test recipe serving changes.
  • Test allergy exclusion.
  • Test ingredient matching.
  • Test ingredient quantity conversion.
  • Test shopping-list aggregation.
  • Swap one meal and verify other meals remain unchanged.
  • Confirm the calendar updates after a meal swap.

C. Training tests

  • Generate plans for two through six training days.
  • Test beginners and experienced users.
  • Test different equipment availability.
  • Test muscle priority selection.
  • Check weekly muscle exposure and recovery spacing.
  • Check that sessions fit the selected duration.
  • Test customized routines.

D. Progressive overload tests

  • Record weights and repetitions.
  • Complete a full session.
  • Confirm historical performance is saved.
  • Confirm next targets are calculated correctly.
  • Confirm an increase is suggested only when criteria are met.
  • Test stalled performance.
  • Test fatigue and pain flags.
  • Confirm previous history is never overwritten.

E. Training mode tests

  • Start a workout.
  • Start and stop timers.
  • Pause and resume.
  • Skip rest.
  • Open exercise instructions.
  • Change between timer and guided mode.
  • Background and foreground the app.
  • Close and reopen the app during a workout.
  • Finish a workout and verify all results persist.

F. Calendar tests

  • Add an event using +.
  • Edit an event.
  • Move an event.
  • Delete an event.
  • Swap a scheduled meal.
  • Start a workout from the calendar.
  • Complete a workout and update its calendar state.
  • Check category colors.
  • Check timezone changes.
  • Check duplicate prevention.

G. Medication tests

  • Add a user-entered medication.
  • Save clinician-provided dosage information.
  • Set reminders.
  • Change reminder times.
  • Mark a reminder taken or skipped.
  • Pause a medication schedule.
  • Verify no generic dose suggestions appear.
  • Verify private data is not exposed in inappropriate places.

H. Notification tests

  • Test first permission request.
  • Test permission denied.
  • Test reminders when the app is closed.
  • Test rescheduling.
  • Test quiet hours.
  • Test daylight-saving changes.
  • Test duplicate prevention.
  • Test notification action buttons.

I. Regression tests

All existing working functionality must remain functional. Test existing onboarding, navigation, account handling, persistence, visual components and other established features.

Automated testing

Use:

  • XCTest for logic.
  • Swift Testing where appropriate.
  • XCUITest for user journeys.
  • Unit tests for nutrition calculations.
  • Unit tests for workout generation.
  • Unit tests for progression rules.
  • Integration tests for calendar and notifications.
